# 分层输入架构迁移

## 目标

候选字串整理不再以“给来源全集逐条判定是不是词”为主线。新的工程目标是把输入职责拆成四层：

```text
基础解码
  -> 静态核心与动态组合共同生成候选
  -> 用户学习调整个人排序
  -> 可选语义排序结合上下文重排
  -> 确定性回退始终保留
```

四层解决的问题不同：

| 层 | 职责 | 不负责 |
|---|---|---|
| 基础解码 | 有来源音节、单字和音元编码的确定性转换 | 猜测新读音、判断词性 |
| 动态组合 | 从已解码组件生成有限候选路径 | 宣称唯一正确分词 |
| 用户学习 | 记录用户词条、选择频率和上下文转移 | 把个人偏好写回通用词典 |
| 语义排序 | 根据上下文给已有候选重排 | 绕过基础解码直接发明读音 |

万象、pypinyin、BCC 和候选整理数据库继续作为来源证据、容量规划和回放材料。通过来源门禁只表示
读音可用，不再等同于必须进入默认静态核心。

## 当前落地状态

### 基础解码

现有 `SyllableEncodingPipeline`、三模式编码、唯一布局投影、单字候选索引和 SQLite/JSON 运行候选
保持不变。这一层不依赖网络和语义模型。

### 动态组合

`recursive_composition_evidence` 是离线覆盖证据。运行时新增 `DynamicCandidateProvider` 接口，提供者
返回的候选被明确标为 `dynamic_composition`；二至七字动态候选可以进入统一排序。首个生产提供者是
轻声回退：仅当完整多音节输入含有正式清单中已准入的轻声音节时，才允许同声韵的一至四声单字读音
临时占据该轻声位置。候选采用有界槽位和束宽，且必须至少实际使用一个轻声回退位置；它不会写回
单字读音或把词内轻声扩张为孤立单字读音。

一般单字组合提供者使用相同的二至七音节窗口。剪枝分三层：

1. 每个音节只保留去重后的高权重、常用单字槽位；
2. 逐音节束搜索，只保留固定数量的高分部分路径；
3. 汇总全部动态提供者后，校验字数与拼音音节数，按字串去重，并限制同首字簇和总候选数。

候选保留逐字组件、数字标调拼音、组合规则和组合分数，便于回放；不会物化完整笛卡尔积。当前尚未
把全量离线递归证据直接接成生产提供者，避免未经回放就把 160 多万项重新变成运行词库。

动态提供者必须满足：

- 只使用正式链已能解码的读音和组件；
- 限制候选数量，不生成完整笛卡尔积；
- 保留组件、规则和来源；
- 不把组合输入序列写成整体来源词音；
- 失败时不影响基础解码。

### 用户学习

`user_lexicon.db` 已保存：

- 用户短语；
- `lookup_code + candidate_text` 的选择频率；
- `previous_text + lookup_code + candidate_text` 的上下文转移频率。

待上屏文本提交时，运行时核对本轮候选选择轨迹。只有提交文本与所选组件完全相等、数字标调拼音
逐字闭合且总长为二至七字时，才以 `auto_learned_committed_sentence` 写入整句；编辑后的文本和
无法验证的手工输入不会自动变成词条。学习失败属于可选层故障，不得阻止文本上屏。

同码排序中，显式选择频次和用户词条优先于公共静态权重；频次键仍是
`lookup_code + candidate_text`，因此一次选择只影响该编码下的该候选。上下文转移重排继续作为更窄的
本地语境层叠加。

上下文转移属于个人本地数据，JSON 备份格式为 schema 2，可随用户词库导出和恢复。文本交换格式仍
只交换明确用户词条及初始频率，不把上下文历史暴露成词条。

### 本地语义排序模拟

`LocalSemanticRankingSimulator` 实现与未来远程排序器相同的候选评分边界。目前它只读取本地真实选择
形成的上下文转移，不声称完成语义理解：

```text
前一已提交文本 + 当前 lookup code + 当前候选
  -> 本地观察频次
  -> 对基础排序结果加上下文分
```

没有观察记录时，候选顺序完全回到原有确定性排序。模拟器不联网、不上传文本、不生成候选、不修改
拼音和编码。将来接入远程算力时，应替换 `SemanticCandidateRanker` 实现，而不是修改基础解码层。

### 静态核心试验导出

`tools/export_core_trial_lexicons.py` 从静态容量模型选取不同总容量的字串，并为每个入选字串保留全部
合规读音。导出器重新调用正式音节编码链和唯一布局投影，不从容量数据库保存或反推 Yinyuan ID、
码元或键位。

当前默认导出六档：52,290、62,290、102,290、111,294、152,290 和 202,290 个不同字串。每档都
带选择清单、输出哈希和来源清单哈希，只能作为回放试验产物，不能仅凭“理论可组合”替换正式运行
词库。

脱离产品维护前，Windows Yime 的首轮独立试验方案采用 202,290 档，对应 221,268 条读音记录。该
段只保留为历史对照，不构成本仓库当前交接路径。真实 librime 对照
表明：

- “连续的过程”在完整库和试验库中均为首选；
- 111,294 与 152,290 档会把“打出了三只手”误排为“打出了三之首”；
- “三只手”按容量证据自然进入 202,290 档后，目标长句恢复为首选；
- 该修复来自容量档扩大和 Rime 动态组句，没有手写整体词条、拼音、音元码或键位。

因此 202,290 档是首轮 Windows 试验基线，不是最终静态核心。后续仍应以更大回放集测量首选率、
首页命中、延迟和用户学习，再决定增删哪些容量区间。

### 202,290 档分层回放基线

Windows 真实 librime 回放已经从两条人工观察句扩展到 1,400 条自动抽样记录。样本直接取自完整
变长词典，并用试验词典做精确成员检查；不手写字串、拼音或编码。回放按字长
`2 / 3 / 4 / 5 / 6 / 7 / 8-12` 和 `in_core / out_of_core` 交叉分成 14 桶，每桶取 100 条高权重
汉字记录。完整库和试验库分别建立真实 Rime 会话，输入去掉词典分隔空格后的连续编码，记录目标
首选、目标首页、试验首选是否等于完整库首选、首页前五项重合和耗时。

| 分组 | 样本数 | 完整库首选目标 | 试验库首选目标 | 完整库首选中的保持率 | 完整库首页中的目标保持率 |
|---|---:|---:|---:|---:|---:|
| 核心内 | 700 | 700 | 700 | 100.0% | 100.0% |
| 核心外 | 700 | 666 | 413 | 62.0% | 59.1% |
| 合计 | 1,400 | 1,366 | 1,113 | 81.5% | 79.6% |

按长度合并核心内外后，首选保持率分别为：二字 68.1%、三字 66.0%、四字 83.0%、五字
81.5%、六字 91.0%、七字 86.5%、八至十二字 92.0%。其中最明显的缺口是核心外二字桶：
完整库首选命中的 66 条中只有 13 条在试验库仍为首选；核心外三字桶为 32.0%。所有核心内长度桶
均为 100.0%。这说明下一轮容量调整应优先验证高权重二、三字组件，而不是按所有长度无差别扩容。

本轮平均处理时间为完整库 807 微秒、试验库 720 微秒；该差异只是同机回放观察值，不应单独解释为
稳定性能结论。抽样刻意让每个长度和成员桶等量，并优先取高权重记录，因此 81.5% 是用于容量档横向
比较的分层回归基线，不代表真实用户输入中有 81.5% 的自然分布保持率。报告同时保留全部逐例结果，
便于后续六档使用同一口径重放。

### 无精简 pypinyin 并集试验

`--include-pinyin-source pypinyin` 可在任一容量档之上并入来源库中所有带精确 pypinyin 证据且通过
门禁的字串。该入口只扩展字串选择，所有读音仍来自统一来源库，编码仍由正式音节链和唯一布局投影
重新生成。当前 pypinyin 有 411,956 个不同 phrase、411,958 条读音记录；其中 101,878 个字串已在
202,290 档内。无精简并集因此得到 512,368 个不同字串、531,346 条读音记录。

使用首轮报告中完全相同的 1,400 个输入重放，避免词典变化同时改变抽样集合：

| 指标 | 202,290 基线 | 基线 + 全量 pypinyin |
|---|---:|---:|
| 首选保持率 | 81.48% | 90.26% |
| 首页目标保持率 | 79.56% | 90.28% |
| 首页前五平均重合 | 3.94 | 4.43 |
| 四字组合首选保持率 | 83.0% | 91.0% |
| 原核心外四字桶首选保持率 | 66.0% | 82.0% |
| 试验库平均处理时间 | 720 微秒 | 719 微秒 |

原核心外 700 条的首选保持率从 62.0% 提升到 80.0%。按扩充后成员关系重新抽取 1,400 条高权重
压力样本时，总体首选保持率为 82.16%，其中新核心外 700 条为 63.77%；这是因为抽样继续移向尚未
纳入的更难长尾，不能与固定语料的 90.26% 直接比较。它说明全量 pypinyin 对既有缺口有效，但没有
消除所有非 pypinyin 二、三字组件问题。当前阶段保留该无精简试验档，不据此修改正式完整词库。

### pypinyin / 万象按字长并集对照

导出器也支持 `--include-source-lengths SOURCE:LENGTHS`，用于在同一 202,290 基础档上按来源和
字长建立可再生并集。以下两组严格重放首轮报告中的同一批 1,400 个输入：

- A：两家二字并集 + pypinyin 三、四字；
- B：两家二、三字并集 + pypinyin 四字。

| 方案 | 不同字串 | 读音记录 | 首选保持率 | 首页保持率 | 二字 | 三字 | 四字 | 五字 | 八至十二字 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 202,290 基线 | 202,290 | 221,268 | 81.48% | 79.56% | 68.07% | 66.0% | 83.0% | 81.5% | 92.0% |
| A | 567,312 | 587,321 | 86.90% | 87.35% | 98.8% | 71.5% | 90.5% | 80.5% | 92.0% |
| B | 1,197,449 | 1,221,616 | 91.95% | 92.35% | 98.8% | 99.5% | 91.0% | 81.0% | 93.5% |
| B-lite（剔除专名类） | 1,148,334 | 1,172,441 | 90.92% | 91.28% | 97.59% | 94.0% | 91.0% | 80.5% | 93.5% |
| 基线 + 全量 pypinyin | 512,368 | 531,346 | 90.26% | 90.28% | 86.14% | 72.0% | 91.0% | 90.5% | 98.5% |

B 的固定样本总体保持率最高，证明万象三字并集对短组件召回很强；代价是读音记录达到全量
pypinyin 方案的约 2.3 倍。全量 pypinyin 方案更小，并在五字以上各组更好。A 的主要价值是以中等
容量把二字组提高到 98.8%，但没有解决三字缺口。该表是历史容量探索记录；A、B 及“202,290 +
全量 pypinyin”均未成为最终 Windows 默认方案。

B-lite 保留万象 `jichu / wuzhong / huaxue / yaopin / duoyin / fangyan / shici` 的二、三字，
剔除 `renming / mingren / yiren / diming` 等专名分类。相对 B 少 49,115 个字串、49,175 条
读音，固定样本首选保持率只下降 1.03 个百分点。B 能保持而 B-lite 失去的 14 条首选全部可追溯到
专名：7 条 `renming`、4 条 `mingren`、1 条 `yiren`、1 条 `diming`，以及受联想专名组件影响的
“江苏苏宁队”。四字、六字、七字和八至十二字组完全不变，说明普通成句质量基本相同，损失集中在
预期的专名召回。不过容量只下降约 4%，因为 `jichu` 本身占万象二、三字材料的绝大部分；若目标是
显著缩容，下一步仍须在基础分类内部按频率和回放证据分层，不能只删除专名分类。

## 当前落地状态与后续顺序

迁移的第一阶段已经完成：Windows 默认运行字典为两级筛选后的1,167,057条映射，其中包含
46,095个已编码单字；前14,000字保持核心排序，其余32,095字位于低频外围。旧大词库退出
安装运行链。固定回放、加速学习漂移和纯净用户态重启闭环均已通过。

后续顺序：

1. 保持当前核心边界，持续收集基础排序、用户选择、重启保持和用户库增长；
2. 将多个开发周期反复出现的高频缺词送入晋升审核，不从单次误选直接提升；
3. 比较静态保留、动态生成和本地语义重排的首选率、翻页率和延迟；
4. 只有跨用户、跨周期证据充分时才调整公共核心；
5. 领域词、万象专名和长尾材料保留在来源/可选领域层；
6. 远程语义排序另行接入；超时、断网、拒绝上传或返回无效结果时必须无缝使用本地顺序。

## 排序边界

语义排序只能重排候选生成层已经提供的字串。若远程模型将来需要提出新字串，该字串仍必须经过：

```text
字串
  -> 来源读音或可验证的动态组件路径
  -> 正式音节编码链
  -> 候选生成层
  -> 语义排序
```

远程结果不得携带或指定 Yinyuan ID、码元、键位，也不得用模型猜测替代缺失的普通话读音来源。
