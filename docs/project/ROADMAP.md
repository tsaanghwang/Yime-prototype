# 项目路线图

## 文档定位

本文记录 2026-07 主线闭合后的工程阶段和下一步优先级。当前已经完成到什么程度，以
[当前实现总览](../CURRENT_ARCHITECTURE.md) 为准；候选语料的规模、分层和整理顺序，以
[候选语料库整理路线图](../CANDIDATE_CORPUS_ROADMAP.md) 为准。

自 2026-08 起，本路线图只覆盖本仓库的历史维护、来源核对、数据清理和恢复研究。Yime 产品编码、
词库、布局、Windows 构建及发布的现行路线图在 `C:\dev\Yime`；本仓库不再安排跨仓交接任务。

路线图不再把已经完成的 N/M 语义真源、三模式生成链、统一来源库或 Windows 前端可消费性验证列为
未来工作，也不把 Python 桌面钩子原型等同于整个 Windows 交付路线。

## 当前阶段

项目当前处于“精简默认运行层已落地，开始用纯净用户态数据稳定排序和词条晋升”的阶段。

```text
上游字词与频次来源
  -> source_lexicon.sqlite3（唯一生产真源）
  -> 1732 项有来源的规范带调音节
  -> 正式音节分析与四个 Yinyuan ID
  -> 等长 / 变长 / 省键三模式
  -> 唯一布局投影
  -> Python 研究原型运行库与历史交接证据
  -X-> Windows 产品构建和发布（转到 C:\dev\Yime）
```

已经落地并受测试或锁检查保护的基础包括：

1. `N01-N27`、`M01-M33` 已由独立语义注册表承载，Yinyuan ID 与字符投影、键位投影分层。
2. `yinjie_code.json`、运行时数据库、resolved layout、KLC 和 crosswalk 已明确为派生或消费产物。
3. 1732 项现行音节采用实例驱动，由正式编码器生成四音元结果；规则缺口会失败并报告。
4. `source_lexicon.sqlite3` 已成为字词、读音、来源证据和频次的唯一生产真源，旧
   `source_pinyin.db` 已退出默认入口和回退链。
5. 等长、变长、省键三模式由同一音元序列确定性派生；键位只从
   `internal_data/manual_key_layout.json` 投影。
6. 原型可以复现完整离线数据和历史两级核心运行词典，但不再生成 Windows 产品交接包。
7. Python 桌面输入法原型仍可用于本地研究和回归；既有 Weasel/Rime 与 PIME 结果只作历史证据。
8. 动态组合扩大回放、加速学习漂移及纯净用户态人工闭环已经完成首轮验收；上下文证据和真实用户
   长期数据仍待积累。

## 贯穿全部阶段的长期维护事务：审音

字词读音审查不是一次性数据清洗，也不能在某一轮 PSC 对照、上游同步或人工复核结束后标记为
“全部完成”。它是原型尚待持续推进的工程维护事务：当前已经建立来源保留、合规门禁、差异审计和
人工裁决基础设施，但全量字词的读音事实、词义分化、语境实现、轻声、儿化及历史来源冲突不可能靠
单一材料一次裁决完毕。

长期维护按以下边界进行：

1. 官方规范、PSC 材料、权威词典、pypinyin、RIME-LMDG（万象）、Unihan 和用户复现都作为分层
   证据保存；任何一个来源都不自动充当全部词条的唯一裁判。
2. “尚无第二来源复核”不等于“读音错误”。来源可追溯、结构合法且没有具体反证的记录可以保留为
   来源实证读音；只有出现明确冲突、结构异常或可靠反证时才进入疑错、暂缓或拒绝通道。
3. 已确认错误不得原样继续编码。修订必须登记原始记录、修订读音、证据、适用词义或语境、裁决人和
   历史；不得静默改写上游文件，也不得由编码结果反推读音。
4. 规范性、是否存在、使用频率、词义或语境、候选排序是不同问题。审音不得顺便用局部材料为全库
   决定所谓“主读音”；高频读音排序应另用有来源的语料或使用统计处理。
5. 每次上游版本更新、规范资料增补、恢复研究和问题报告都可以触发新一轮审计。单轮任务可以按
   输入指纹、待复核队列、已裁决记录和回归结果闭合，但“审音维护”本身长期保持开放。

当前 PSC 通道先执行独立的“来源材料转录校核”，只确认汉字—拼音记录是否忠实于来源；原型读音仅
作发现转录异常的旁侧参考，不处理轻声主次、读音排序或原型修订。具体流程见
[PSC 来源材料转录校核与后续读音审计](PSC_PRONUNCIATION_SOURCE_AUDIT.md)。来源转录层完成后，才另立
读音证据审计和可撤销修订任务；两阶段不得共用裁决按钮或把“转录正确”解释成“应成为原型主读”。
在该闭环完成前，审音仍属于“基础设施已部分落地、长期内容审查尚未完成”。

## 当前最高优先级

### 1. 候选池动态覆盖闭环（已完成）

目标：从“来源与编码正确”推进到“每个已编码候选都有可解释的动态/静态职责”。

2026-07-28 完成：

- 固定来源包、递归组合、静态容量、两级运行选择和只读报告；
- 以 R0–R5 为 2,441,908 个已编码字串逐一分层，R0 为 0，完成门禁通过；
- 把低频、古旧、助词构式和暂不可达材料从“删除判断”中分离；
- 将 472,671 个可动态恢复的零证据长串迁出静态核心，选中违规为 0；
- 把 R1–R3 留作动态核心持续提升队列，而不是未完成的删除清单。

完成证据见 [动态候选覆盖与核心提升闭环](../DYNAMIC_CANDIDATE_COVERAGE.md)；持续工作只更新残差、
排序和回放指标，不再把本项恢复为待做。

候选排序的长尾结构也已完成程序闭环：BCC 为主证据，RIME-LMDG 只补 BCC 空缺，两者都缺失时
以静态效用作明确标注的非频次保底。见[候选排序证据与长尾结构](../CANDIDATE_RANKING_EVIDENCE.md)。

### 2. 固定脱离产品维护边界

目标：让本仓库保持可研究、可追溯和可恢复，同时不能重新成为产品构建或交接源。

近期工作：

- 保持来源、审计和历史派生关系可复现，不把离线结果重新接入 Windows 安装链；
- 阻断便携包、Setup、MSKLC、部署和 Windows Yime 交接入口，并用回归测试防止复活；
- 不读取或写入 `C:\dev\Yime`，不通过共享数据库、同级目录或环境变量建立隐式耦合；
- 需要转移的清理结果必须先授权，再按内容哈希导出到独立非 Git 归档；
- 产品仓库对任何一次性导出独立做来源审查，不恢复自动交接关系。

完整边界见[脱离产品维护边界](../DETACHED_MAINTENANCE_BOUNDARY.md)；旧结构见
[Windows Yime 交接历史记录](WINDOWS_YIME_LEXICON_HANDOFF.md)。

### 3. 提升真实输入稳定性

目标：稳定仅用于研究的 Python 原型，不把本仓库工作扩张到系统前端。

近期工作：

- 用户词库和学习数据按布局摘要隔离，避免旧布局学习记录污染当前布局。

### 4. 继续清理过时入口和测试假设

目标：让新参与者从入口文档得到当前事实，而不是重走历史分支。

近期工作：

## 中期目标

### 1. 完成高频候选整理和多读音分层

- 为第二批 BCC 频次 1,000–9,999 的字串形成可解释建议队列；
- 整理高频多读音、词内轻声、专名读音和历史来源冲突；
- 引入 KWIC、邻接频次、左右熵、互信息及保守类别规则；
- 机器或 LLM 只提出可审查建议，不填写无来源拼音或编码。

### 2. 持续验证历史候选筛选层

- 只使用已批准组件和来源库中已有的合规读音；
- 通过回放比较召回、排序、歧义、内存和速度；
- 只将跨周期高频且审核通过的真实缺词晋升为公共候选；
- 保持旧大词库离线，不以个别压力样本为理由整体回装。

### 3. 保持恢复出口可审计

- 为确需转移的清理结果记录授权、内容哈希、来源和独立归档位置；
- 验证一次性导出不依赖共享可变数据库或本仓库路径；
- 把历史安装、升级和回滚资料保留为证据，不在本仓库恢复执行入口；
- 产品试用、安装包和真实应用烟测全部留给 `C:\dev\Yime`。

## 长期研究与扩展

### 1. 片音语音实验

当前工程只验证符号化音节分析和编码。片音边界、最短听知时限、不同说话人一致性以及插值重建
自然度仍需独立语音实验，不能从四元位置或 Yinyuan ID 反推已经得到实验结论。

### 2. 更强的候选模型

在人工决策集和回放基线形成后，再评估统计模型、语言模型建议、用户自适应排序及领域词库分包。
模型输出必须保留证据和不确定性，不能覆盖来源事实。

### 3. 更多平台

移动端、浏览器端和其他产品平台不属于本仓库路线图；相关评估只在 `C:\dev\Yime` 进行。本仓库可
保留与历史语义、来源和布局有关的研究材料，但不得向产品平台自动发布。

## 暂不优先

1. 为展示效果另写一套 Web 编码逻辑；
2. 在候选回放前大规模删除静态词条；
3. 让 AI 为未登记拼音猜读音、四音元码或键位；
4. 从本仓库直接修补或覆盖产品仓库；
5. 把语音学待验证假设写成已经实现的声学能力。

## 维护原则

1. 当前事实、已完成里程碑和未来目标必须分开。
2. 来源事实、候选决策、音元语义和布局投影必须分层。
3. 新形式没有依据时失败并报告，不以单项手写结果推进进度。
4. 路线图中的动态数字只作快照；长期统计以重新构建后的 manifest 和报告为准。
5. 如果本文与 `CURRENT_ARCHITECTURE.md` 冲突，先核实实现，再立即修正文档。
